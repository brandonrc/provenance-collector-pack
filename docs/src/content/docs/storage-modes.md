## What replaced `persistence.mode`

provenance-collector-pack 0.1.x moved one JSON file per run from the collector
CronJob to its dashboard, chosen by `persistence.mode` (`http` upload,
shared `pvc`, or `configmap`). None of that exists any more:

- The worker runs the collector itself and writes the results to **Postgres**;
  there is no upload endpoint, shared report volume or ConfigMap sink.
- Report history is **per scan**: inventory, provenance and posture results are
  kept for the last 10 completed scans (not `reportRetention` files). The
  provenance report for a scan is rendered on request at
  `/api/reports/provenance-<timestamp>.json`.
- Setting `persistence.mode` fails the render with a pointer here; old report
  files are **not** imported.

## What is stored where

| Data | Where | Value |
|---|---|---|
| Scans, inventory, findings, scores, provenance, Helm releases, assertion runs, settings, report metadata | Postgres database `posture` | `persistence.postgres` (10Gi), StatefulSet volume |
| Clair's vulnerability and index data | Postgres database `clair` (same server) | (shares the Postgres volume; budget several GiB) |
| Grype DB, skopeo scratch, clairctl state, sigstore TUF cache | worker cache PVC `<fullname>-worker-cache` | `persistence.worker` (20Gi) |
| Trivy vulnerability DB | `<fullname>-trivy-cache` | `persistence.trivy` (10Gi) |
| Generated report files (POA&M, CKLB, SAR, OSCAL, exports) | `<fullname>-reports`, mounted in api **and** worker | `persistence.reports` (2Gi), newest `reports.keepPerType` per type |

With `persistence.enabled: false` everything except Postgres's own volume
claim becomes an `emptyDir`: scanner databases re-download on every restart and
reports generated by the worker are not downloadable.

## Access modes and scheduling

All volumes default to `ReadWriteOnce`. Because the api and the worker both
mount the reports volume, the worker gets a required pod affinity to the api pod
(unless `worker.affinity` is set) so both land on the node that holds it. An
RWX storage class removes that constraint.

## Lifecycle

The worker, Trivy and reports PVCs are part of the Helm release: `helm
uninstall` deletes them (they carry no `helm.sh/resource-policy: keep`). The
Postgres data PVC comes from the StatefulSet's `volumeClaimTemplates` and the
generated database Secret is annotated `keep`, so both survive an uninstall and
are reused by a reinstall with the same release name.

## External database

`postgresql.enabled: false` with `externalDatabase.*` points the api, worker
and Clair at an existing server. Both databases (`posture`, `clair`) must exist
and be owned by the configured user; Clair also needs the `uuid-ossp` extension.
